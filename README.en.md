# Guitarbook · 吉他宝典

[简体中文](README.md) · [English](README.en.md) · [日本語](README.ja.md)

A Flutter guitar toolkit for practicing and improvising: build a groove with the drum machine, layer phrases with the Looper, and shape your sound with live effects.

## Drum machine × Looper × Effects

- **Drum machine:** 6 time signatures (4/4, 3/4, 2/4, 5/4, 6/8, 7/8) and 22 practice grooves—rock, funk, blues, pop, folk, punk, metal, disco, reggae, hip-hop, jazz swing and Latin in 4/4, plus waltz and swing waltz in 3/4, fast punk and march in 2/4, progressive rock and five-beat swing in 5/4, six-eight swing and slow blues in 6/8, and avant-garde rock and Balkan in 7/8. Edit kick, snare, hi-hat, clap and conga in a one-bar sixteenth-note grid (4 steps per beat in x/4, 2 per beat in x/8); set 30–240 BPM, swing, track mutes and playback volume.
- **Looper:** record a first loop from 0.3 to 30 seconds and build up to 6 layers. Undo the latest layer, delete any single layer (with one undo for the deletion), stop/resume or clear everything. Smart first-layer recording measures background noise, starts when you play and trims the ends after about two seconds of silence. Bind keyboard keys or a USB footswitch that sends keyboard input.
- **Live effects:** fuzz, compressor, reverb, overdrive, delay, switchable manual/automatic wah and a pitch shifter, plus four original amp styles: American clean, British chime, British rock and modern high gain. Chain up to 8 instances, drag to reorder, adjust independent parameters and bypass pedals. Linux and Windows also load locally installed, compatible VST3 effects, and can use a gamepad's analog trigger as a wah expression pedal. A desktop browser build offers the same built-in pedals and amps (implemented in this round; automated whole-page testing passed, real-hardware tone pending; no VST3 and no wet Looper) and now reads the gamepad's analog trigger through the browser Gamepad API.
- **One workspace:** the home screen now shows a single “Jam workspace” card — the separate live-effects entry was removed, because the effects already live in the workspace. Opening it gives drums, Looper and effects on one scrolling page with separate volume controls; the pedalboard sits at the bottom of the page, so scroll down to reach it. Entering the workspace only probes the effects engine and the audio devices and does not start monitoring on its own, so press the monitoring control in the effects area to hear your guitar. On Android, iOS, Linux and Windows, the Looper captures the processed signal after the effects chain; monitoring must be active and the actual sample rate must be 48 kHz.
- **Smart bass:** a new automatic bass line in the workspace. It recognises the chord you are playing and arranges a bass line that matches the drum machine's BPM, time signature and kick pattern, sample-for-sample as long as one drum bar; three styles (follow the kick, root pulse, walking bass), its own volume, chord changes land on the next beat, and switching it off releases the microphone.

The toolkit also includes a standard-tuning guitar tuner, metronome, scale fretboard and beginner chord lessons. README translations do not imply a translated app interface.

## Start playing

1. Run from source, then open the jam workspace from the home screen (the “Jam workspace” card; there is no separate live-effects entry any more). The page stacks the drum machine, the Looper and the effects board in one scrolling column — the effects board is at the bottom, so scroll down for it. Pick a time signature, choose a groove for it and press the start control. Switching the time signature loads that signature's default groove and keeps your tempo and volume.
2. For live effects, connect your guitar to an audio interface and headphones to that same interface. Start at low headphone volume. Entering the workspace only probes the engine and the devices silently; press the monitoring control in the effects area at the bottom of the workspace to hear your guitar. In a desktop browser that same click unlocks the audio and asks for microphone permission.
3. On supported effects platforms, start monitoring at 48 kHz before recording the first Looper layer. On macOS/Web, allow microphone access and use interface direct monitoring if needed. Press the main Looper control again to finish a layer and play it back; press again to overdub.
4. Default shortcuts: **Space** records/overdubs, **S** stops/resumes, **Z** undoes the latest layer, **X** clears all layers. Customize bindings in Looper settings; the app must have focus. Smart recording applies only to the first layer.
5. To drop a single recorded layer, tap the **×** in the top-right corner of that layer's tile in the layer strip. The remaining layers keep the same loop length and stay in phase; the hint bar offers one **Undo** for the deletion. Deleting the last remaining layer stops the loop and resets the loop length. Deleting is refused while recording or while the loop is still loading.

Use headphones to avoid feedback and recording the backing track. Drums require no microphone permission; recording, tuning and live effects require audio-input access. Android requires API 24 or later. Apple platforms require microphone permission; Windows must allow microphone access. Linux raw-input recording requires `parecord`, `pactl` and `ffmpeg`. Web requires HTTPS or localhost, microphone permission and a user gesture to unlock audio.

Add “哇音 Wah” and drag its position knob to sweep 350–2200 Hz (position 0–1, default 0.5). Resonance Q is 0.5–8 (2), mix 0–1 (1), and output 0–1 (0.7). Switch between manual (default) and automatic modes on the pedal. Automatic mode exposes speed (0.1–5 Hz, default 1) and depth (0–1, default 0.8), sweeping around the position setting. On Linux and Windows desktop, and in a desktop browser, an optional gamepad analog trigger can drive the wah position as an expression pedal (see below). Wah shares Android/iOS/Linux/Windows DSP; device listening remains unverified.

Add “移调” (pitch) to shift the whole guitar sound up or down by up to 12 semitones: the transpose knob runs from −12 to +12 semitones (default 0 keeps the original pitch), mix 0–1 (default 1) blends dry against wet and 0 semitones passes the dry signal through untouched, and output 0–1 (default 1) sets the level. The algorithm reads a ~30 ms ring buffer through two cross-faded read heads, so the wet signal trails the dry signal by roughly 30 ms and sounds slightly metallic; it does not time-stretch, so the playing speed stays the same. Android / iOS / Linux / Windows and the desktop browser share the same pitch-shifting DSP. Dragging the transpose knob quickly between −12 and +12 interrupts the cross-fade, so the wet signal can step audibly; that is inherent to the algorithm, not a fault.

Pitch shifter verification (2026-11-05): static analysis is clean (`flutter analyze lib test`), the full Flutter test suite passes 264 tests (including a new test that adds the pitch pedal and adjusts its three knobs independently), and the Linux Debug and Web Release builds succeed. Native and web share one specification: the desktop host `--test-builtins` run and the offline mobile C++ test binary both pass (built-in DSP tests, mobile-chain wet capture and lifecycle tests), the Node offline regression passes 13 / 13 (4 new pitch cases) and the browser DSP run passes 38 / 38. Covered: sample-exact pass-through at 0 semitones, ±12 semitones scaling the fundamental by 2^(n/12) (measured +12 → 440.4 Hz, −12 → 109.8 Hz, +7 → 328.8 Hz, −5 → 164.9 Hz), mix 0 passing the dry signal through, output 0 muting, parameter changes without NaN / clipping / clicks, independent instances, and finite output at 44.1 / 48 / 96 kHz with extreme parameters. Android / iOS / Windows were not built this round; real playing by ear and external audio-interface behaviour are still unverified.


Mobile effects use the current system audio route and mono input, with no in-app route picker or external VST3 support. Desktop device settings allow input/output and buffer selection; Windows does not bundle the ASIO SDK. Bluetooth is not a low-latency reference output.

On Linux the effects host captures the **system default input** and never guesses a source. PipeWire splits an interface like the Focusrite Scarlett into `Input 1 Inst/Line`, `Input 2 Mic` and a `Monitor Input 3+4` loopback node, and the default is not necessarily the jack the guitar is plugged into. If the default points at the microphone or the loopback, the app receives that node instead of the guitar: direct monitoring is audible, but the software gets silence. The page then says “没有收到任何输入数据”; set the system default input to the guitar's Inst/Line node (on this machine `wpctl set-default 65` selects `Input 1 Inst/Line`) and press the reconnect action. The notice only appears after 3 s of **exact digital silence**, so pauses while playing do not trigger it. Measured on 2026-11-03: with the loopback as default every sample was 0 and `inputPeak` stayed 0; after pointing at `Input 1 Inst/Line` the idle noise floor was 1.2e-4–1.9e-4 and the notice stayed off for 6 s.

Desktop browser effects (this round's implementation): a desktop browser (Chrome / Edge) offers the same built-in pedals and amps through Web Audio's AudioWorklet, with the DSP ported from the native C++/JUCE code to JavaScript. Connect the guitar to an audio interface and headphones to that same interface, turn off the interface's direct monitoring, then press the monitoring control and grant microphone access — the browser needs that user gesture to unlock audio, and the page must be served over HTTPS or localhost. ## Gamepad trigger expression pedal (Linux / Windows / desktop browser, Linux disconnect loop fixed 2026-11-03)

On Linux and Windows desktop, and in a desktop browser, a gamepad's analog trigger can act as a wah expression pedal. The feature is off by default: add “哇音 Wah”, enable the “gamepad trigger → wah pedal” card below the pedalboard, choose the left or right trigger and the target wah instance, and optionally invert and calibrate its range. Trigger readings are written to the wah position parameter (350–2200 Hz) at a 25 ms throttle. Position is only written while the target wah is in manual mode, monitoring is running and a trigger reading exists; automatic wah mode, stopped monitoring, no wah in the chain or no selected target skip writes and explain why in the card. Disabling the switch or leaving the page releases the input device.

**After switching to the fixed build, do a hot restart or restart the app**: hot reload does not replace code in an already-running isolate.

The three platforms read the trigger differently:

- **Linux desktop** reads `/dev/input/event*` directly: gamepads with an analog trigger axis are discovered from `/proc/bus/input/devices`, hot-plug reconnection is supported, and the driver's actual axis range is read when available (commonly 0–255 or 0–1023). Most desktop sessions already grant access through the udev `uaccess` rule; on this machine (Ubuntu 26.04 VM) the current user could read `/dev/input/event20` through its ACL on 2026-11-03, so permission was not the cause of the failure. If `getfacl` shows no entry for the user, add them to the `input` group (`sudo usermod -aG input $USER`, then log in again) or install a udev rule: create `/etc/udev/rules.d/99-gamepad.rules` containing `KERNEL=="event*", SUBSYSTEM=="input", MODE="0660", TAG+="uaccess"`, then run `sudo udevadm control --reload-rules && sudo udevadm trigger`. Flatpak/Snap sandboxes may block `/dev/input`. **If `event*` cannot be opened for permission reasons the app falls back to the legacy joystick interface** (`/dev/input/js*`, `0664` by default, readable by any user without the `input` group): the kernel scales axis values to -32767..32767 with 0 as the middle, which the app converts back to 0–255 before driving the wah; evdev is still preferred whenever it can be opened, because only it reports the driver's real range. The Linux reader runs a non-blocking `open` + `poll` loop in a separate isolate: when a signal interrupts `poll` (`EINTR`) it retries with the remaining timeout, and `read` treats only EOF as a disconnect — `EAGAIN` or an empty read keeps polling.
- **Windows desktop** polls XInput for the left/right trigger (0–255) and recognises XInput-compatible (Xbox-family) controllers only; PlayStation controllers need Steam Input or DS4Windows mapping first.
- **Desktop browser** uses the browser Gamepad API and reads the analog value of buttons 6 (L2) and 7 (R2) in the standard gamepad mapping (the browser normalises it to 0–1, which is converted to 0–255 here). The browser normally only hands a controller to the page after the user has pressed a button on it, and the page has to stay in the foreground because background tabs get throttled. When no controller is found the card lists the three steps to take: press a button on the controller, keep the page in the foreground, and on Linux make sure the browser can read `/dev/input/event*` (join the `input` group or install a udev uaccess rule; without Chrome's official rules the browser cannot see the controller either). Controllers without the standard mapping (digital triggers) are reported explicitly by name.

**Confirm read permission first, but this was not the 2026-11-03 failure**: `event*` nodes are `0660 root:input` by default and a user outside the `input` group usually cannot read them; however, systemd's 70-uaccess rule tags the logged-in seat0 user, and xpad-style controllers also carry `ID_INPUT_JOYSTICK` on their `event*` nodes, so most desktop sessions already have access. On this machine the current user could read `/dev/input/event20` through its ACL (`getfacl /dev/input/event20` confirms it), the device was online and it opened normally — the earlier conclusion that permission was the blocker is withdrawn. The browser needs the same access because the browser process itself reads `/dev/input` (Chrome cannot enumerate the controller without its official `60-chrome-devices.rules`; the snap build of Firefox has the joystick interface connected and usually works out of the box). Only if `getfacl` shows no entry for the current user, grant access as follows: a uaccess rule needs no re-login, while adding the user to the `input` group does. Flatpak / Snap sandboxes may also block `/dev/input`:

```bash
echo 'KERNEL=="event*", SUBSYSTEM=="input", MODE="0660", GROUP="input", TAG+="uaccess"' | sudo tee /etc/udev/rules.d/99-gamepad.rules
sudo udevadm control --reload-rules && sudo udevadm trigger
```

That single command fixes the desktop build and the browser build together (once the browser can read the controller, the web build works). Adding the user to the `input` group (`sudo usermod -aG input $USER`) works too, but only after a re-login. Wireless sleep, a dropped Bluetooth link or a lost USB passthrough in a virtual machine can remove the device node (on this machine the controller was online on 2026-11-03, so this was not the cause of the failure); when the system does not list it at all, the card reports how many input devices were scanned. The repository ships a diagnostic script that shows which step is stuck:

```bash
build/flutter-sdk/bin/dart run tool/probe_gamepad.dart
```

It lists the input devices of the system, which ones carry an analog trigger axis, the permissions of `/dev/input/event*` and `/dev/input/js*` and whether they can be opened, and then runs the real input source once and prints its snapshots. Run it in the host desktop session (sandboxes and containers cannot see `/dev/input`); this is also the tool that, together with `dart --profiler`, reproduced the once-a-second disconnect loop and confirmed after the fix that it was gone.

Status messages (improved 2026-11-02): the card now distinguishes “not enabled”, “searching for a gamepad”, “connected: <device>” and concrete failure reasons. A failure to read `/proc` is reported as an error and explains that containers, virtual machines or restricted sandboxes may not see the input device list; a detected gamepad without an analog trigger (for example a Switch Pro whose ZL/ZR are digital buttons) is named; when no gamepad is found at all the card reports how many input devices were scanned and notes that wireless sleep, a dropped Bluetooth link or a lost USB passthrough in a virtual machine all remove the device node, so the controller must be woken up and shown as online in the system gamepad settings. Android, iOS and macOS still show the unsupported note.

Verification (2026-11-03): the whole-page browser test (real `build/web` output plus desktop Chrome headless with an injected standard-mapping fake gamepad, `tool/check_web_gamepad_page.mjs`) passed 11 / 11 that day and was re-run on 2026-11-04, passing 12 / 12 (the path now enters through the home screen’s “Jam workspace”, with one extra assertion that the page scrolls down to the effects area below the workspace): the card shows “connected: Flydigi Apex 5”, the raw reading follows the trigger 128 → 230 → 0, the pedal position percentage tracks it, and after unplugging the card reports “gamepad disconnected, searching again…”. The previous round's static analysis and full 206-test Flutter suite passed. Checks: `flutter analyze` (`lib/features/expression_pedal`, `tool/probe_gamepad.dart`) is clean; `flutter test test/linux_gamepad_trigger_source_test.dart test/linux_evdev_test.dart test/linux_joystick_test.dart` passes all 40 tests; `dart --profiler tool/probe_gamepad.dart 12` prints a single `status=ready device=Flydigi Apex 5 range=0-255` (before the fix it alternated ready / searching about once a second). **GUI end-to-end verification (2026-11-03, 01:05–01:20)**: a separate instance built from the fixed code was started with `build/flutter-sdk/bin/flutter run -d linux --pid-file .tools/verify_app.pid lib/main.dart`, with the profiler still enabled (`getFlagList`: profiler=true, profile_period=1000 — the same condition that reproduced the failure), and a real window was driven through `/dev/uinput` keyboard injection (Tab/Enter: open the jam workspace, focus the “enable gamepad pedal” switch and press Enter). ## Smart bass (2026-11-05)

Smart bass is the workspace's automatic bass line: it listens to the guitar you are playing, works out the chord, and arranges a bass line that follows the drum machine's tempo, time signature and kick pattern — you only play chords.

The panel sits between the drums/Looper area and the effects board and offers:

- **On/off**: “Start smart bass” begins listening and playing the bass; pressing it again stops and releases the microphone.
- **Current chord**: shows the recognised chord (C major, Am, G7 …). Two consecutive matching analyses are needed before the label changes, so pauses while playing do not make it flicker.
- **Style**: follow the kick, root pulse (a fixed root position each bar) or walking bass (one chord tone per beat).
- **Volume**: 0–100 %, independent of the drum machine and the Looper.

Using it:

1. Pick the time signature, groove and tempo in the drum machine first — the bass is arranged from the drum machine's current BPM, signature and kick hits.
2. A chord change never lands mid-beat: it is queued for the next beat. The bass loop is sample-for-sample as long as one drum bar, so it does not drift; the phase against the drums is checked every 400 ms and re-aligned whenever it differs by more than 120 ms.
3. On Android, iOS, Linux and Windows the smart bass listens to the processed (wet) signal, so monitoring must be running at 48 kHz in the effects area first; otherwise it asks you to start monitoring. macOS and the browser use the raw microphone input. The browser additionally needs HTTPS or localhost, microphone permission and a user gesture to unlock audio.
4. The smart bass shares the same input as the session recorder and the Looper, so no second microphone is opened; the microphone indicator in the page header lights up while it runs. Use headphones.
5. With a silent or very noisy input it recognises nothing and stays quiet, keeping the previous result.

Limits: only one chord is recognised at a time (no polychord detection, no melody following); the bass is a synthesised sine plus harmonics with roots from E1 to A2, not a sampled instrument; recognition and synthesis add a little CPU on phones. Recognition accuracy is limited: in a regression with synthetic signals, roughly 10–13 of 16 chords had both the root and the quality right, depending on the register. The mistakes concentrate in low-position chords whose root is below about 130 Hz and in sus4 / dominant-seventh shapes, where the overlapping fundamentals leave only the harmonics to go on.

Verification (2026-11-05): static analysis is clean, the full Flutter test suite passes 263 tests, and `flutter build linux --debug` and `flutter build web --release` succeed. Real playing by ear on the six platforms is still unverified.

## Session recording

The workspace recorder mixes drums, Looper playback and live input into a 48 kHz mono WAV. Select 8–128 MiB (default 32 MiB, about 5.8 minutes); once full, it overwrites the oldest audio. Stop to preview or save. Starting again replaces the unsaved take. Backgrounding stops recording; leaving clears unsaved audio. Effects platforms require monitoring at 48 kHz; live input is captured after effects, before monitor volume. Drums and Looper gains affect the mix. Use headphones; loud mixes clip. Drum and Looper stems are phase-anchored on the first recorded block, advanced by the recorded input frames and drift-corrected slowly (at most 0.2% per block), re-anchoring only when the engine position jumps more than 100 ms; this avoids the per-block timeline tearing caused by the engine's 512-frame (about 10.7 ms) position quantization. Multiple engines are not hardware synchronized, and a fixed first-block offset of up to one buffer remains.

Native saves go to `Guitarbook Recordings` inside the application documents directory, with the path shown. iOS enables Files access; Android currently uses private app storage, removed on uninstall, without a share sheet or folder chooser. Web starts a browser download. Preview/export and playback use memory beyond the recording limit. Device audio and file-access checks remain pending; see the Chinese README for current automated checks.

## Current limits

Drums and Looper run independently: there is no automatic beat synchronization, quantization or time stretching. Unsaved audio stays in local memory and is cleared when leaving the workspace; the session recorder can save a mixed WAV. Audio is not uploaded. Effect chains, device choices and workspace settings are not persisted. Backgrounding stops playback/monitoring; returning does not restart it automatically. No MIDI or global background shortcuts are integrated. The gamepad trigger is used only for wah expression, not for Looper pedal bindings.

Built-in amps use original algorithms and simple cabinet filtering, without IR convolution or oversampling. Third-party plugins must match the host OS and CPU architecture; they are not bundled. Driver-reported latency is not a physical round-trip measurement. Real-device sound, USB interface compatibility and long-running stability still need verification.

Drum machine: the grid is one bar only — there are no multi-bar patterns, no automatic fills, no sample import and no preset saving. Whether more drum pieces should be added is still open. Looper: one loop per take, up to 30 seconds and 6 layers, no per-layer length trimming and no per-layer volume.

Smart bass: drums and Looper still run independently, but the smart bass is sample-aligned with the drum machine (the Looper is not). ## Run from source

No official installer or hosted app is currently provided. Install Flutter with Dart matching `pubspec.yaml` (currently `^3.12.0`) and the target platform toolchain.

```bash
flutter doctor
flutter pub get
flutter devices
flutter run -d <device-id>
```

Desktop targets can use `linux`, `windows` or `macos`; Web can use `chrome`. iOS builds require macOS and Xcode. Native effects builds fetch JUCE 8.0.12 on first build and require CMake/C++ tooling; Android also needs the NDK and CMake 3.22.1. Follow the dependency licensing requirements, including JUCE's AGPLv3/commercial terms.

See the [detailed Chinese setup and usage guide](README.md), [desktop effects host guide](native/effects_host/README.md), [mobile effects guide](native/mobile_effects/README.md) and [current feature design](docs/FEATURES.md) for dependencies, diagnostics and verification records.

## PRs welcome

Contributions to drum grooves and sound, Looper workflow and synchronization, effects DSP, platform support, accessibility, translations and documentation are welcome! Open an issue first for substantial design changes.

1. Read [AGENTS.md](AGENTS.md) and [docs/FEATURES.md](docs/FEATURES.md).
2. Run `flutter analyze` and `flutter test`; include relevant native build/test results for audio changes.
3. Update affected README translations and feature designs when behavior changes. State which platforms/devices were tested and what remains unverified.

Device reports are valuable too: include your OS, audio interface, sample rate/buffer, reproduction steps and results. Please do not include third-party plugins, restricted sound assets or personal recordings in contributions.
